Q1 策略

OMNI 和 Arova Nexus 是同一個產品的兩個版本，還是兩條獨立產品線？

官網對外只提 Nexus，但 arova-ai-core 的內部文案列了 EWAI OMNI、NEXUS、EWAI FLOW 三個產品。要釐清的是：

  • Nexus 和 OMNI 是兩條獨立產品線，還是同產品在不同客戶/通路的分支？
  • 對外只賣 Nexus、對內 OMNI 給特定客戶嗎？

初步推論 · 2026-04-24

Nexus 和 OMNI 看起來是兩條獨立的產品線，不是同一產品的不同版本。

推論依據

  1. 對外品牌一致指向 Nexus（官網只提 Nexus）
  2. 對外客戶證據只看得到 Nexus，OMNI v1 找不到客戶部署
  3. 技術選型差距大（LLM / ORM / 整合系統 / 目標語系全部不同），更像針對不同客戶情境獨立設計

→ 若推論成立軟體部主要接手 nexus-demo + nexus-docs，omni-v2 與 arova-ai-core 可暫排除。

對上述推論的態度

Q3 策略

nexus-demo 到底是 demo，還是客戶的實際環境？

repo 名稱是 nexus-demo，但 README 寫「deployed to production at nexus-demo.ewill.dev」、版號 v1.5.0-stable、openspec 多次提到「客戶泰國廠 Phase 2.5 / 2.6」。直接決定軟體部的 SLA 承諾、oncall 規劃、事故處理流程。

初步推論 · 2026-04-24

目前不是客戶的生產系統，更接近 (a) demo 或 (c) PoC 評估環境。

主要訊號

  1. 命名直接點明用途：repo 叫 nexus-demo、網域是 nexus-demo.ewill.dev，即使 ewill 是自家公司網域，nexus-demo 這個前綴本身就宣告了「展示用途」，真實客戶使用的系統通常會掛在客戶方網域（例：it.thailand-factory.com）或客戶專屬子網域，不會跟 demo 共用前綴
  2. 「客戶泰國廠 Phase 2.5 / 2.6」還停在 openspec 的 proposal 狀態：proposal 代表「提案中、尚未實作」，如果泰國廠真的在用生產版本，這些應該是「已交付給客戶的下一階段」，而不是還在提案，這更像是銷售 / PoC 流程的階段被冠上產品版本號
  3. nexus-docs 整體仍是 Phase 0「產品定義階段」：若已有客戶使用，文件站不會停留在「產品定義中」，至少會有 user guide 或 admin manual
  4. 客戶部署文件實體不存在：nexus-docs/CLAUDE.md 提及 docs/architecture/customer/（「客戶泰國廠 series」），但該目錄在 repo 中不存在，對客戶負責的生產系統，客戶部署文件通常是最完整的，這個目錄缺席本身就是訊號

次要訊號

  1. 產品版本號（v1.5.0）超前 PRD（v1.3）——這是 demo 產品的典型特徵（工程師迭代快過 PRD 跟進）；客戶產品通常相反，PRD 會先鎖版再出對應版本
  2. nexus-demo 沒有 CODEOWNERS，對客戶負責的 repo 通常會有 review 流程把關

對上述推論的態度

Q4 策略

OMNI v1 到底由哪幾個 repo 組成？

多份文件把「OMNI v1」說成「前端 ewai-omni + 後端 arova-ai-core」，但這個說法尚未正式確認，且 ewai-omni 找不到原始碼。若拼圖不正確，handoff 範圍與 omni-v2 取代 v1 的可行性都會失去依據。

初步推論 · 2026-04-24

「OMNI v1 = ewai-omni + arova-ai-core」主架構大致正確，但 v1 完整範圍還不確定（可能還有排程 / 背景工作 / ETL / 管理後台 / 行動端等元件）。

推論依據

  1. 三份不同 repo 的文件都指向「前端 + 後端」結構，難以是巧合
  2. omni-v2 的程式套件名 ewai-omni-v2 是接續版本
  3. arova-ai-core 自述「共用的 AI 後端引擎」與後端角色對得上

→ 若推論不成立handoff 範圍不完整，Q3 判斷基礎需重新評估，並需補完 v1 完整清單（併入 Q6-1）。

對上述推論的態度
